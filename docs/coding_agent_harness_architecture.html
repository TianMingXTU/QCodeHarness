目标方案 / 产品化汇报版 · 非现状验收

Rust Coding Agent Harness · 产品架构与执行流程

面向 AI 编程场景，采用 Rust 构建可扩展 Coding Agent Harness，参考 Codex、Claude Code、DeepSeek 类成熟形态，形成“多智能体 + 工具体系 + MCP 接入 + 审批与安全 + 可观测与评测”的完整平台。AI 负责执行，工程师负责审查、决策与验收。

01 / 总体平台架构

该架构强调“模型能力”与“工程执行能力”分离：大模型提供推理与规划，Rust Harness 负责流程编排、工具调用、权限控制、上下文管理和执行证据沉淀。适合向甲方说明平台完整性，而不仅是一个简单聊天机器人。

02 / 多智能体协作架构

面向较复杂的编码任务，平台可采用“多智能体分工协作”模式。每个 Agent 承担清晰职责，统一由 Harness 编排，避免职责混乱。这样更贴近当前主流 Coding Agent 产品的产品形态，也便于甲方理解“为什么效率更高”。

Planner Agent规划者
  • 理解用户需求
  • 拆解任务与子步骤
  • 决定调用哪些 Agent
  • 控制整体执行节奏
Coder Agent编码者
  • 分析代码结构
  • 搜索相关实现
  • 生成补丁与代码修改
  • 根据测试结果继续修复
Reviewer Agent评审者
  • 检查改动合理性
  • 识别风险和副作用
  • 检查规范与可维护性
  • 给出是否建议合并
Tester Agent验证者
  • 运行编译与测试
  • 收集失败日志
  • 驱动回归测试
  • 输出验证结论
Memory / Summary Agent沉淀者
  • 沉淀任务结论
  • 维护会话摘要
  • 更新知识与经验库
  • 便于后续任务复用
↓ Harness 统一编排 / 调度 / 审批 / 记录 ↓
统一调度中心决定哪个 Agent 在何时介入，并回收执行结果。
统一权限中心不同 Agent 不直接获取全部权限，统一经策略层审批。
共享上下文与状态各 Agent 共享必要状态，但按职责读取，减少上下文混乱。
共享工具池文件、Shell、Git、测试、MCP 工具可供不同 Agent 复用。

适合的任务

复杂缺陷排查、较大功能开发、重构、批量代码治理、自动化测试补齐等更适合使用多 Agent 模式。

对甲方的价值

职责明确、流程清晰、可解释性更强，也更适合后续接入组织内的审批、知识库和研发规范。

不是为了炫技

多智能体不是越多越好，而是在复杂任务中通过分工提高稳定性、审查质量和任务闭环能力。

第一阶段落地

首版可先做“Planner + Coder + Tester + Reviewer”的轻量组合，后续再补记忆和知识沉淀能力。

03 / 标准任务执行流程

该流程适用于“修复 Bug、增加功能、补测试、代码重构”等主流 AI 编程任务。汇报时可直接用来讲解：AI 如何从任务输入一路走到输出结果，以及人类工程师介入的位置在哪里。

典型场景：工程师下发“修复当前项目中的失败测试并给出改动说明”。平台会自动分析代码、拆解步骤、执行工具、运行测试、反复修复并汇总结果，最终由工程师审核是否接受。

流程核心

不是“一次性生成代码”，而是多轮循环执行：规划、调用工具、观察结果、继续修复、最终交付。

关键控制点

审批、权限、预算、超时、上下文和终止条件都由 Harness 管理，而不是交给模型自由发挥。

适合甲方解释

可直接讲成：系统像一个受控的 AI 工程团队，有规划、有执行、有测试、有审核、有交付。

真实落地价值

流程标准化之后，后续可以持续扩展企业规范、知识库、工单系统、发布系统和组织内审计要求。

04 / 工具体系与 MCP 接入架构

主流 AI 编程平台的一个共同点是：不仅有内部工具，还需要通过标准协议接入更多外部能力。这里把“本地工具池”和“MCP / 外部系统接入”分开，方便甲方理解系统扩展性。

A. 平台内置工具池开箱即用
文件与代码工具读写文件、目录浏览、全文搜索、代码片段定位、补丁编辑。
命令与执行工具Shell、编译、测试、Lint、格式化、构建命令。
Git 工具查看 diff、状态、分支信息、提交建议、回滚辅助。
验证与诊断工具日志分析、错误定位、性能检查、测试报告采集。
文档与知识工具读取 README、设计文档、API 文档、编码规范。
浏览器 / API 工具调用接口、页面验证、联调辅助、环境健康检查。
B. MCP / 外部系统接入标准协议扩展
MCP Server通过标准协议暴露企业内部工具与服务能力。
知识库 / 文档中心设计文档、规范文档、组件文档、团队经验库。
研发系统工单、需求、缺陷平台、CI/CD、代码托管系统。
质量与测试系统自动化测试平台、质量门禁、覆盖率和扫描服务。
运维与监控系统日志平台、告警平台、配置中心、环境信息服务。
组织能力沉淀审批流、审计系统、成本中心、知识沉淀与报表。
MCP 的价值：不是只接一个工具，而是把平台变成可持续扩展的“AI 工程能力中台”。
工具调用模板（面向 Coding Agent）固定工作模板
Bug 修复模板读取错误 → 搜索定位 → 修改代码 → 跑测试 → 回归 → 汇总。
功能开发模板理解需求 → 拆解步骤 → 新增实现 → 增加测试 → 验证。
代码评审模板读取 diff → 理解上下文 → 识别风险 → 给出建议。
重构模板分析结构 → 设计改造 → 分阶段修改 → 验证兼容性。
对甲方的价值表达业务口径
更标准

把研发过程抽象成固定模板，降低人和项目差异。

更可控

所有工具调用都在 Harness 管控之下，保留证据。

更可扩展

通过 MCP 持续接入组织内已有研发与运维能力。

更易产品化

从单点工具升级为可落地的平台能力，便于后续扩展。

05 / 实施边界与甲方汇报口径

本页用于甲方汇报时统一口径：哪些能力是第一阶段重点，哪些是后续增强；同时避免把“目标方案”误讲成“已经全部落地”。

第一阶段重点（优先落地）

  • Rust CLI 形态的基础 Coding Agent Harness。
  • 具备单任务多轮执行能力：规划、工具调用、测试、结果汇总。
  • 内置核心工具：文件、搜索、编辑、Shell、测试、Git。
  • 支持轻量多 Agent：Planner、Coder、Tester、Reviewer。
  • 支持基础审批、超时、日志记录、会话保存与结果审查。
  • 可在测试仓库中完成真实 Bug 修复和功能开发验证。

后续增强方向（产品化演进）

  • Web 界面 / IDE 集成 / 企业级多用户协作。
  • 更多 MCP Server 接入与组织内系统打通。
  • 更成熟的沙箱隔离、审计与安全治理。
  • 知识库、项目长期记忆、经验复用能力。
  • 任务基准集、成功率评测、成本与效率分析报表。
  • 更丰富的工作流模板与行业化定制能力。

汇报建议 1

先讲总体架构，再讲多智能体，再讲单个任务怎么跑完，最后讲工具和 MCP，甲方更容易听懂。

汇报建议 2

重点强调平台可控、可扩展、可审计，不要只强调模型聪明。甲方更在意可用性与可管理性。

汇报建议 3

用“AI 工程团队”类比解释最容易理解：有规划、有编码、有测试、有评审、有沉淀。
