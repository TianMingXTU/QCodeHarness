# 商业化形态评估（决策输入）

本文件只整理三种候选交付形态的成本项、约束、待验证假设和需要人工拍板的阻塞点。它是决策输入，不是产品承诺、定价方案或市场预测；当前代码不据此新增计费、鉴权、租户或云端能力。现有本地 Web UI 按单机单用户设计，事件与审批证据来自同一份 `TaskService` 账本，任何商业化形态都不能绕过该证据链。

## 共同前提

- 事件账本：`events.jsonl` / 事件广播记录任务创建、工具请求、审批等待、审批决定和完成；对外形态可以重排展示，不能改写、删减或推断缺失的审批事实。
- 审批闸门：涉及写入、外部执行或策略要求的操作仍走 ToolGuard、审批闸门和证据账本；商业化形态不能把 UI 按钮变成隐式授权。
- 隔离与平台能力：工作区隔离、沙箱、模型连接和机器凭据的行为随平台能力变化；包装形态不能假定所有平台具备同等能力。
- 数据与凭据：用户源码、模型请求内容、工具输出、日志、API Key 和 Git 凭据的处理方式必须先明确边界，再决定能否托管或计量。
- 发行与维护：现有单机 CLI、常驻服务、本地 Web UI 的升级路径、证据格式兼容、回滚和离线恢复都要计入维护成本。
- 桌面壳（Electron/Tauri）只是未来可选项：仅当本地 Web UI 稳定并完成体验验证后再评估，本轮不实现。

## 形态一：订阅

交付思路是个人或团队按周期获得软件使用权与升级服务，运行时仍以用户本机为主。

成本项：

- 许可证或服务开通、续期、失效后的降级路径。
- 多平台二进制、签名、升级通道、补丁分发与旧证据格式兼容。
- 用户支持、缺陷复现所需日志脱敏与授权、版本维护窗口。
- 若支持团队共用配置，需要配置同步、权限边界和审计，但不应自动变成远程多用户。

合规与证据约束：

- 订阅状态不应影响证据账本的完整性；到期后仍须允许读取和导出本机已有证据。
- 许可证校验若联网，应说明传输的数据范围；不得把源码内容、工具输出或凭据作为校验负载。
- 审批链证据保留 `approval_waiting`、`approval_resolved` 和对应审计事件；订阅层级不能省略审批记录。

待验证假设：

- 目标用户是否接受本机运行、由自己保管源码和凭据。
- 续费价值主要来自持续维护还是新增能力；现有证据无法确认。
- 离线使用多久仍可接受，以及到期后只读导出的边界是否够用。

需要人工决策的阻塞点：

- 是否引入账号体系和许可证校验；引入后隐私声明与离线承诺如何写。
- 订阅对象按人、按机器还是按组织；未确定前不做配额或鉴权代码。
- 是否承诺固定更新周期、支持期限和兼容范围。

## 形态二：按量

交付思路是以可计量的运行单位结算，例如模型调用、任务执行或工具调用。当前事件账本已有模型调用和工具调用相关事件，但尚需确认它们能否作为一致、不可重复且可被用户核对的计量口径。

成本项：

- 计量口径定义、口径变更记录、重复上报与重放去重、本地对账导出。
- 模型供应商成本、失败调用归属、重试和上下文压缩产生的额外调用如何展示。
- 计量数据留存、账单争议复核、审计日志和与现有证据的时间线关联。
- 预算耗尽、断网、计量服务不可用时的明确行为，以及不因计量故障丢失既有证据。

合规与证据约束：

- 计量字段必须能追溯到服务事件；不能用独立旁路计数器生成无法核对的账单。
- 账单数据应排除源码正文、工具输出正文和凭据；如需传输，只传最少必要标识与数量。
- 审批拒绝、重放、重试、中断和跨进程委派每一级都要与计量单位有明确映射，避免把未执行的调用计入。

待验证假设：

- 现有 `AuditEvent` / `ServiceEvent` 是否足以覆盖所有需要计量的调用，是否存在无法归因的后台操作。
- 用户是否信任本地可核对的账单明细，以及能否接受计量服务的联网依赖。
- 不同模型、不同执行路径和失败重试的成本差异是否能用同一口径表达。

需要人工决策的阻塞点：

- 结算单位选模型调用、任务还是工具调用；口径未定前不写计费逻辑。
- 失败调用、重试、审批拒绝是否计入，以及争议处理窗口。
- 是否允许预付费额度、预算上限自动停止，以及停止后如何保留审批证据。

## 形态三：托管

交付思路是由服务方运行计算环境，用户通过远端界面提交任务。这与当前单机单用户前提冲突最大；在明确边界前不实现。

成本项：

- 计算资源、工作区生命周期、并发隔离、依赖缓存、任务超时和整树终止。
- 每个租户的代码、凭据、模型调用、日志与证据的隔离、加密、备份、删除和导出。
- 网络入口、身份认证、权限、审计、漏洞响应、容量监控、事故演练和值班。
- 托管环境的沙箱与宿主机边界、恶意工具调用防护、供应链与依赖更新。
- 跨区域数据处理、可用性承诺、灾备和退出迁移的运维成本。

合规与证据约束：

- 托管后仍需证明事件账本未被服务方或并发任务改写；证据导出要包含版本、序列、任务上下文和审批链。
- 用户源码、凭据和工具输出的访问范围必须可审计；运维排障不能变成无限读取。
- 审批决定必须绑定到具体任务、执行和审批请求；跨进程委派帧不能被合并成不可追溯的结果。
- 数据保留期限、删除请求与法律保全要求冲突时，先由人工确定处置流程。

待验证假设：

- 是否存在用户愿意把源码和凭据交由服务方环境处理的场景。
- 当前工作区隔离、Job Object / 进程组终止和平台能力是否足以支撑多任务并发。
- 证据账本在托管环境中如何防篡改、如何向用户证明完整性。
- 现有单机服务协议能否扩展为远端协议而不破坏 CLI 与本地 Web UI 的事件语义。

需要人工决策的阻塞点：

- 是否接受多租户模型和远程访问；本轮明确不做，改变该前提需重新评审安全边界。
- 隔离粒度、凭据托管策略、数据驻留区域和删除/导出责任。
- 服务等级、事故通报、责任边界、供应商数据处理协议和合规审查清单。
- 托管失败时用户能否继续使用本机 CLI 和已有证据，以及迁移格式由谁维护。

## 决策前必须补齐的信息

- 真实用户访谈与试用数据：谁运行、在哪运行、源码和凭据能否离机、愿意为什么付费。
- 可复核的成本测量：在现有基准和事件账本上统计模型调用、重试、失败、工具执行与存储占用，不引用未经验证的外部市场数字。
- 数据分类清单和法务确认：哪些字段可离开本机、保存多久、谁可访问、如何删除。
- 三种形态共用的证据导出格式与兼容性测试；任何形态都先通过 CLI 与本地 Web UI 的证据语义对账。
- 明确责任人分别拍板产品边界、定价口径、隐私合规和运维承诺；未拍板前只保留本机单机能力。
